# ADR: Initial Architecture Baseline

- Date: 2026-09-08
- Status: accepted
- Area: simulation foundation

## Decision summary

The initial system will use:

- a fixed discrete tick simulation
- a single-threaded deterministic engine
- seeded randomness
- immutable events plus periodic SQLite snapshots
- a simple 2D grid world
- structured action proposals validated by the engine
- inhabitant decisions at configurable intervals, with urgent interruptions
- radius-based perception with explicit uncertainty
- structured SQLite-backed memories; no vector database initially
- a local Ollama model adapter using `gemma4:e2b`
- a read-only browser observer over a client-independent event/state API

## 1. Time model

Use discrete ticks. Every tick runs in a known phase order:

1. apply scheduled effects and environmental changes
2. update needs and body conditions
3. generate perceptions
4. run inhabitants whose decision interval or urgent trigger is due
5. collect action proposals
6. validate and resolve proposals
7. emit events
8. update memories and beliefs
9. persist the tick result

The default decision interval is configurable and should not require one LLM request per tick. The initial default may be several ticks, with urgent triggers for immediate danger or major unexpected events.

## 2. Determinism and concurrency

The simulation engine is single-threaded and deterministic for a given world state, seed, event history, and recorded model outputs. LLM requests may happen outside the engine, but their results are committed only at a tick boundary.

Every random operation uses the simulation’s seeded random source. Systems must not use uncontrolled global randomness.

## 3. State and persistence

SQLite stores both an append-only event log and periodic world snapshots. Events are the explanation of change; snapshots are a performance optimization for replay. Each run records its seed, scenario, software version, model identifier, model settings, and prompt/context inputs.

Replay reuses recorded LLM outputs. It does not call the model again and hope for equivalent behavior.

## 4. World representation

Start with a 2D grid. Inhabitants and objects occupy cells, movement is explicit, and terrain can block or constrain actions. Use a world interface rather than spreading grid assumptions through every system so continuous coordinates or richer geometry can be added later if needed.

The initial grid is a research representation, not a permanent game-world commitment.

## 5. Actions and conflicts

Inhabitants submit one structured action proposal per decision:

```json
{
  "type": "move",
  "target": {"x": 4, "y": 8},
  "duration": 1
}
```

The engine validates action type, parameters, capabilities, timing, and current world conditions. Invalid proposals become explicit failed actions and do not mutate state.

Actions are atomic at resolution time. Longer activities are represented as engine-owned in-progress actions, not by allowing an inhabitant to mutate state over multiple calls.

When proposals conflict, the engine resolves them using explicit system rules over a stable deterministic ordering. Inhabitant identity must not silently become a permanent priority advantage.

## 6. Perception and information

Inhabitants initially perceive a bounded radius around their current cell. Perception is generated by the engine and may include uncertainty, omissions, and noisy attributes. The inhabitant receives its observation, not the authoritative world state.

Communication creates a new observation attributed to the sender. It does not reveal truth automatically.

## 7. Inhabitant cognition and model use

The inhabitant runtime owns beliefs, desires, memory, planning, and communication. Needs and basic body updates remain deterministic engine concerns.

The LLM receives a compact structured context containing current perception, selected memories, active desires, current plan, and descriptions of capabilities available to the inhabitant. It returns a structured proposal. It must not return executable code or direct state changes.

Descriptions must not reveal hidden world facts merely because an action is currently legal. The engine validates proposed actions against authoritative state and exposes the result through subsequent perceivable consequences.

Model explanations are optional diagnostic text. They are not treated as ground truth or as privileged access to hidden reasoning.

## 8. Memory

Use structured SQLite records for the initial memory system. Retrieval uses explicit fields such as relevance, recency, salience, confidence, and provenance. Start without vector search; add semantic retrieval only if experiments show that structured retrieval is inadequate.

Memories, beliefs, and testimony remain distinct records. The engine preserves ownership and provenance.

## 9. Observer

The first observer is a local browser client. It consumes read models, state snapshots, and an event stream through a client-independent API. Normal observation is read-only.

Pause, resume, and branching are explicit simulation-control commands that produce recorded control events. A future Godot client should consume the same protocol rather than require changes to the simulation engine.

## 10. Deferred decisions

The following are intentionally deferred:

- continuous physics
- ECS architecture
- microservices
- vector databases
- complex ecology
- advanced crafting and social institutions
- Godot rendering

They should be introduced only when a measured requirement justifies them.

## Rationale

This baseline minimizes hidden nondeterminism, keeps the local model workload manageable, and makes the first experiments easy to inspect and reproduce. It also preserves clear seams for richer world simulation, alternate models, and future visual clients.
